# Единый документ: Task Tracker внутри корпоративного мессенджера

## 1. Общая информация

### 1.1. Название

Модуль: **Task Tracker**

### 1.2. Контекст

В корпоративном мессенджере уже реализовано ядро обмена сообщениями и звонков. Необходимо добавить встроенный таск-трекер для постановки, ведения и контроля задач внутри компании.

Предполагаемый размер организации: около 30 сотрудников.

### 1.3. Цель

Создать встроенный таск-трекер, который позволит:

* создавать и вести задачи без использования внешних сервисов;
* настраивать структуру задач через админ-панель;
* разделять задачи по шаблонам;
* хранить историю изменений;
* обсуждать задачи в комментариях;
* прикладывать файлы;
* использовать подзадачи.

---

# 2. PRD

## 2.1. Продуктовая цель

Добавить в корпоративный мессенджер простой и расширяемый таск-трекер, который покрывает ежедневную постановку задач внутри компании и при этом не перегружен сложной бизнес-логикой.

## 2.2. Проблема

Сейчас коммуникация происходит в мессенджере, но задачи:

* теряются в сообщениях;
* не имеют единого статуса;
* не имеют формализованных исполнителей;
* не имеют истории изменений;
* не имеют структурированного списка, фильтрации и поиска;
* не привязаны к управляемому жизненному циклу.

## 2.3. Решение

Встроить в мессенджер модуль Task Tracker с:

* несколькими шаблонами задач;
* системными и пользовательскими полями;
* настраиваемыми справочниками enum;
* комментариями;
* вложениями;
* историей изменений;
* подзадачами;
* уведомлениями по ключевым событиям.

## 2.4. Целевая аудитория

* все сотрудники компании;
* тимлиды;
* менеджеры;
* администраторы системы.

## 2.5. Продуктовые принципы MVP

* минимально необходимый функционал;
* простая модель прав;
* отсутствие сложного workflow;
* расширяемая архитектура;
* прозрачность изменений;
* единый опыт работы внутри уже существующего мессенджера.

## 2.6. Пользовательские сценарии

### Сценарий 1. Создание задачи

Пользователь открывает форму создания задачи, выбирает шаблон, заполняет поля и сохраняет задачу.

### Сценарий 2. Назначение исполнителей

Пользователь указывает одного или нескольких исполнителей. Назначенным пользователям приходят уведомления.

### Сценарий 3. Изменение статуса

Пользователь меняет статус задачи. Изменение фиксируется в истории, исполнители получают уведомления.

### Сценарий 4. Работа с подзадачами

Пользователь создаёт подзадачи для декомпозиции основной задачи.

### Сценарий 6. Комментирование

Пользователь оставляет комментарии в задаче для фиксации обсуждения.

### Сценарий 7. Вложения

Пользователь прикрепляет файлы к задаче.

### Сценарий 8. Работа администратора

Администратор:

* создаёт шаблоны задач;
* управляет полями внутри шаблонов;
* управляет статусами;
* управляет глобальными enum-справочниками.

## 2.7. Что входит в MVP

* несколько шаблонов задач;
* выбор шаблона при создании задачи;
* `sort_order` шаблона, при создании задачи показываем список шаблонов в соответствии с `sort_order`;
* префикс шаблона в идентификаторе задачи;
* системные поля задачи;
* конструктор пользовательских полей;
* типы полей: `text`, `number`, `user`, `users`, `enum`, `multi_enum`, `date`, `datetime`;
* глобальные enum-справочники;
* версионирование enum-справочников;
* подзадачи;
* вложения;
* комментарии;
* история изменений;
* список задач в виде таблицы;
* поиск;
* фильтрация;
* сортировка;
* группировка по статусу;
* уведомления при назначении исполнителя и смене статуса.

## 2.8. Что не входит в MVP

* kanban;
* saved views;
* ограничения переходов между статусами;
* права доступа на уровне отдельных задач;
* условная логика полей;
* сложные валидации;
* связь задач с чатами и сообщениями;
* автоматизация и правила;
* зависимости между задачами;
* несколько уровней workflow;
* миграция задачи между шаблонами;
* физическое удаление шаблонов;
* физическое удаление статусов;
* физическое удаление полей шаблона;
* треды комментариев.

## 2.9. Критерии успеха

Качественные:

* сотрудники могут вести задачи внутри мессенджера;
* задачи не теряются в чатах;
* видны статусы, исполнители и история;
* администратор может управлять структурой задач без участия разработчика.

Функциональные:

* система поддерживает несколько типов задач через шаблоны;
* структура задачи определяется шаблоном;
* исторические данные не ломаются после изменения шаблонов и справочников.

# 3. Техническое задание

## 3.1. Основные сущности

### 3.1.1. Шаблон задачи

Шаблон задачи определяет тип задачи и её структуру.

Каждый шаблон содержит:

* `prefix`
* набор пользовательских полей
* порядок полей
* признак удаления

Шаблон используется при создании задачи.

### 3.1.2. Задача

Задача — основная сущность трекера. Каждая задача создаётся по выбранному шаблону.

### 3.1.3. Пользовательские поля

Поля, которые определяются в шаблоне и задают дополнительную структуру задачи.

### 3.1.4. Enum-справочник

Глобальный справочник значений, который может использоваться в enum-полях шаблонов.

### 3.1.5. Подзадача

Задача, привязанная к родительской задаче.

### 3.1.7. Вложение

Файл, прикреплённый к задаче.

### 3.1.8. Комментарий

Комментарий пользователя в карточке задачи.

### 3.1.9. История изменений

Аудит всех ключевых изменений задачи и связанных сущностей.

---

## 3.2. Шаблоны задач

### 3.2.1. Общие правила

В системе существует несколько шаблонов задач.

Каждый шаблон имеет:

* `id`
* `prefix`
* `sort_order`
* `created_at`
* `updated_at`
* `deleted_at`
* `created_by`
* `updated_by`

### 3.2.2. Правила работы с шаблонами

1. При создании задачи пользователь выбирает шаблон.
2. Если шаблон не выбран, используется шаблон с наименьшим `sort_order`.
3. Удаление шаблона выполняется только через soft delete.
4. Удалённый шаблон нельзя использовать для создания новых задач.
5. Старые задачи, созданные по удалённому шаблону, должны открываться и отображаться корректно.
6. Если активных шаблонов не осталось, создание новых задач невозможно.
7. `prefix` шаблона должен быть **уникальным в системе**.
8. `prefix` может содержать только **латинские символы верхнего регистра** (`A-Z`).
9. `prefix` нельзя изменять, если по шаблону уже создана хотя бы одна задача.

### 3.2.3. Политика изменения шаблонов

Изменение структуры шаблона не должно ломать уже существующие задачи.

При soft delete:

* шаблон остаётся в БД;
* старые задачи продолжают ссылаться на него;
* в UI создания задачи такой шаблон не показывается.

---

## 3.3. Идентификатор задачи

### 3.3.1. Формат

Публичный идентификатор задачи имеет вид:

`<PREFIX>-<N>`

Примеры:

* `DEV-100`
* `QA-45`

### 3.3.2. Правила генерации

1. `PREFIX` берётся из поля `prefix` выбранного шаблона.
2. Числовая часть увеличивается последовательно.
3. Последовательность ведётся отдельно для каждого шаблона.
4. Идентификатор должен быть уникальным во всей системе.
5. После удаления шаблона старые идентификаторы задач не меняются.
6. При изменении шаблона уже созданные задачи не переименовываются.

### 3.3.3. Хранение

У задачи должны храниться:

* `template_id`
* `template_snapshot_prefix`
* `sequence_number`
* `public_id`

Это требуется для устойчивого отображения истории, даже если шаблон позже будет изменён или удалён.

## 3.4. Системные поля задачи

Обязательные системные поля:

* `id`
* `public_id`
* `title`
* `description`
* `status_id`

Служебные поля:

* `template_id`
* `template_snapshot_prefix`
* `sequence_number`
* `created_by`
* `updated_by`
* `created_at`
* `updated_at`
* `parent_task_id`

---

## 3.5. Статусы задач

### 3.5.1. Общая модель

Статус задачи — системный enum, управляемый из админ-панели.

### 3.5.2. Правила

1. Статусы можно удалять только через soft delete.
2. Статусы можно свободно редактировать.
3. Можно добавлять новые статусы.
4. Можно менять порядок статусов.
5. Ограничений на переходы между статусами нет.
6. Старые задачи с удалённым статусом должны корректно отображаться.
7. Удалённый статус не должен предлагаться для выбора в новых изменениях.

---

## 3.6. Пользовательские поля шаблона

### 3.6.1. Типы полей

Поддерживаемые типы:

* `text`
* `number`
* `user`
* `users`
* `enum`
* `multi_enum`
* `date`
* `datetime`

### 3.6.2. Структура поля

Каждое поле шаблона должно содержать:

* `id`
* `template_id`
* `code`
* `name`
* `type`
* `required`
* `sort_order`
* `enum_dictionary_id` — только для enum-полей
* `field_role` nullable
* `created_at`
* `updated_at`
* `deleted_at`

### 3.6.3. Настройки поля

На текущем этапе для поля поддерживается только:

* обязательное / необязательное.

Также обязателен настраиваемый порядок отображения полей.

### 3.6.4. Ограничения MVP

Не поддерживаются:

* условная видимость;
* regex/маски/валидации;
* min/max;
* кастомные правила отображения;
* вычисляемые поля.

### 3.6.5. Роль поля исполнителей

Для определения поля исполнителей используется `field_role = assignee`.

Правила:

1. Поле с ролью `assignee` может иметь только тип `user` или `users`.
2. В рамках одного шаблона допускается не более одного поля с ролью `assignee`.
3. Определение поля исполнителей по `code` не используется.
4. `code` поля должен быть уникален в рамках одного шаблона.

---

## 3.7. Enum-справочники

### 3.7.1. Общая модель

Enum-справочники являются глобальными и используются в полях типов:

* `enum`
* `multi_enum`

### 3.7.2. Структура справочника

Справочник:

* `id`
* `code`
* `name`
* `current_version`
* `created_at`
* `updated_at`

Версия справочника:

* `id`
* `dictionary_id`
* `version`
* `created_at`
* `created_by`

Элемент версии:

* `id`
* `dictionary_version_id`
* `value_code`
* `value_name`
* `sort_order`
* `is_active`

### 3.7.3. Версионирование

Критичное изменение справочника создаёт новую версию:

* `version = version + 1`

Критичным изменением считается:

* удаление значения.

Добавление или переименование значения не считается критичным (ломающим) и не должно приводить к инкременту версии.

### 3.7.4. Хранение в задаче

При сохранении значения enum в задаче необходимо хранить:

* идентификатор или код справочника;
* версию справочника;
* выбранные `value_code`.

Это нужно для корректного отображения исторических данных, даже если справочник позже изменится.

### 3.7.5. Ограничения

* `code` enum-справочника должен быть уникален в системе.

---

## 3.8. Подзадачи

### 3.8.1. Модель

Подзадача является задачей того же типа, что и обычная задача (хранится в той же таблице), но содержит `parent_task_id`.

### 3.8.2. Правила

1. Подзадача создаётся внутри родительской задачи.
2. Для MVP поддерживается только один уровень вложенности.
3. Задача, у которой уже заполнен `parent_task_id`, не может быть родительской задачей для другой задачи.
4. Подзадача не может ссылаться сама на себя.
5. Циклические связи недопустимы.
6. Ограничение на один уровень вложенности должно быть зафиксировано на backend и на уровне DDL.
7. Подзадачи отображаются внутри карточки родительской задачи.

   * `id`
   * `task_id`

   * `storage_key`

Физическое хранение в S3 (Minio).

## 3.11. Комментарии

### 3.11.1. Требования

2. Пользователь не может редактировать собственный комментарий.
3. Комментарии отображаются в хронологическом порядке.
4. Треды комментариев на MVP не требуются.

### 3.11.2. Структура

* `id`
* `task_id`
* `author_id`
* `body`
* `created_at`
* `updated_at`

## 3.12. История изменений

### 3.12.1. Назначение

Система должна вести историю изменений задачи.

### 3.12.2. В историю должны попадать

* создание задачи;
* изменение системных полей;
* изменение пользовательских полей;
* изменение статуса;
* изменение исполнителей;
* создание, изменение, удаление подзадач;
* добавление и удаление вложений;
* создание комментариев.

### 3.12.3. Формат события

* `id`
* `task_id`
* `actor_id`
* `event_type`
* `entity_type`
* `entity_id`
* `field_code`
* `old_value_json`
* `new_value_json`
* `created_at`

### 3.12.4. Требования к UI

История должна отображаться в человекочитаемом виде.

## 3.13. Права доступа

### 3.13.1. Пользовательские права

Для MVP:

* любой пользователь может создавать задачи;
* любой пользователь может редактировать задачи;
* любой пользователь может просматривать задачи;
* любой пользователь может комментировать задачи.

### 3.13.2. Административные права

Только администраторы могут:

* создавать и редактировать шаблоны;
* удалять шаблоны через soft delete;
* управлять статусами;
* управлять enum-справочниками.

## 3.14. Уведомления

### 3.14.1. События уведомлений

Необходимо отправлять уведомления при:

* назначении исполнителя;
* смене статуса задачи.

### 3.14.2. Правила

1. Уведомления отправляются только при фактическом изменении значения.
2. Если пользователь уже был назначен и состав исполнителей не изменился, дублирующее уведомление не отправляется.
3. При назначении нескольких исполнителей уведомление получают все новые назначенные пользователи.
4. При изменении статуса уведомления отправляются исполнителям задачи.
5. Если в шаблоне отсутствует поле исполнителей, уведомления по исполнителям не отправляются.

### 3.14.3. Практический нюанс

Так как шаблон допускает произвольные поля типа `user/users`, необходимо в реализации определить механизм, по которому система понимает, какое поле является полем исполнителей.

Поле исполнителей определяется через `field_role = assignee`.

Допустимые типы такого поля:

* `user`
* `users`

Определение по `code` не используется.

Функции:

### 3.15.2. Раздел “Статусы”

Функции:

* изменение порядка;

### 3.15.3. Раздел “Enum-справочники”

Функции:

* создание справочника;
* редактирование справочника;
* сохранение новой версии;
* просмотр истории версий.

## 3.16. Пользовательский интерфейс

### 3.16.1. Список задач

Необходим экран списка задач в виде таблицы.

Поддерживаемые возможности:

* поиск;
* фильтрация;
* сортировка;
* группировка по статусу.

Минимальные колонки:

* ID задачи;
* заголовок;
* статус;
* дата создания;
* дата обновления.

Дополнительно могут показываться поля шаблона по расширяемой логике.

### 3.16.2. Поиск

Поиск должен работать по:

* `public_id`
* `title`
* `description`

### 3.16.3. Фильтрация

Фильтрация должна поддерживать:

* статус;
* prefix;
* пользователей в полях типов `user/users`;
* значения `enum/multi_enum`;
* даты при наличии соответствующих полей.

### 3.16.4. Сортировка

Сортировка должна поддерживать:

* ID;
* заголовок;
* статус;
* дату создания;
* дату обновления;
* числовые поля.

### 3.16.5. Группировка

На MVP требуется группировка только по статусу.

### 3.16.6. Карточка задачи

Карточка задачи должна включать:

* системные поля;
* пользовательские поля выбранного шаблона;
* блок подзадач;
* блок вложений;
* блок комментариев;
* блок истории изменений.

---

## 3.17. Выбор шаблона при создании задачи

### 3.17.1. Поведение формы

1. При открытии формы создания задачи выбираем шаблон с минимальным `sort_order`.
2. Пользователь может выбрать другой активный шаблон.
3. После смены шаблона набор полей перестраивается согласно выбранному шаблону.
4. Удалённые шаблоны не должны отображаться в выборе.
5. Если шаблон был удалён в момент, когда пользователь уже заполнил форму, backend при сохранении должен вернуть бизнес-ошибку.

## 3.18. Нефункциональные требования

1. Все изменения должны логироваться в истории.
2. Изменение шаблона не должно ломать существующие задачи.
3. Изменение enum-справочника не должно ломать существующие задачи и историю.
4. Генерация ID должна быть устойчива к гонкам.
5. Архитектура должна быть готова к будущему расширению:

   * kanban;
   * workflow-правила;
   * объектные права;
   * связь задач с чатами;
   * автоматизация;
   * несколько уровней шаблонов.

## 4.2. DoD по backend

### 4.2.1. Шаблоны

* можно создать несколько шаблонов;
* у шаблона есть `prefix`;

* `prefix` нельзя изменить, если по шаблону уже создана хотя бы одна задача.

### 4.2.2. Генерация ID

* при создании задачи генерируется `public_id` вида `PREFIX-N`;

* нумерация независима для каждого шаблона;

### 4.2.3. Поля шаблона

* можно добавить поле любого поддерживаемого типа;

* изменение шаблона не ломает старые задачи;
* `code` поля уникален в рамках шаблона;
* поле исполнителей определяется через `field_role = assignee`;

### 4.2.4. Статусы

* можно создать и отредактировать статус;
* можно менять порядок статусов;

# 5. Граничные случаи

1. Удаляется единственный активный шаблон.  
   Создание новых задач становится невозможным, пока не появится новый активный шаблон.

2. Попытка создать или обновить шаблон с уже существующим `prefix`.  
   Backend возвращает ошибку валидации.

3. Попытка создать или обновить шаблон с `prefix`, содержащим символы вне `A-Z`.  
   Backend возвращает ошибку валидации.

4. Пользователь начал создавать задачу по активному шаблону, но до сохранения шаблон был удалён.  
   Backend возвращает бизнес-ошибку.

5. Попытка изменить `prefix` шаблона, по которому уже создана хотя бы одна задача.  
   Backend возвращает бизнес-ошибку.

6. Поле было удалено из шаблона через soft delete, но в старых задачах по нему есть данные.  
   Данные должны читаться и отображаться как архивные.

7. Значение enum было изменено или удалено в новой версии справочника.  
   Старые задачи продолжают отображать историческое значение по своей версии справочника.

8. Статус удалён через soft delete, но у старой задачи он используется.  
   Задача отображается корректно, но статус не предлагается для новых изменений.

9. Подзадача не должна становиться родителем самой себе.  
   Цикл запрещён на backend.

10. Подзадача не может иметь собственные подзадачи.  
    Backend и DDL запрещают вложенность глубже одного уровня.

11. При повторном сохранении задачи без фактической смены исполнителей уведомления не отправляются.

12. При смене шаблона в форме создания задачи набор полей должен полностью перестраиваться под новый шаблон.

13. В шаблоне отсутствует поле с `field_role = assignee`.  
    Назначение исполнителей и уведомления по исполнителям не работают для такого шаблона.

14. Попытка создать два поля с одинаковым `code` в рамках одного шаблона.  
    Backend возвращает ошибку валидации.

15. Попытка создать enum-справочник с уже существующим `code`.  
    Backend возвращает ошибку валидации.

---

# 6. Архитектурные рекомендации

1. Для генерации последовательности ID использовать отдельную таблицу счётчиков `task_template_sequence` или эквивалентный механизм с транзакционной блокировкой.
2. Для значений пользовательских полей использовать универсальную модель хранения с typed columns + `value_json`.
3. Для устойчивости исторического отображения хранить snapshot-поля шаблона в задаче.
4. Для enum-значений всегда сохранять версию справочника.
5. Для soft delete не использовать физическое удаление шаблонов, статусов, полей шаблона и исторически значимых сущностей. Состояние soft delete определяется только по `deleted_at IS NOT NULL`.
6. Для уведомлений использовать `field_role = assignee` как единственный механизм определения поля исполнителей.
7. Ограничение уникальности `prefix` должно быть закреплено на уровне БД.
8. Ограничение формата `prefix` только на латиницу верхнего регистра должно быть закреплено на уровне БД.
9. Ограничение уникальности `task_field_definition.code` в рамках шаблона должно быть закреплено на уровне БД.
10. Ограничение уникальности `enum_dictionary.code` должно быть закреплено на уровне БД.
11. Ограничение на один уровень вложенности подзадач должно быть закреплено на backend и, где возможно, на уровне DDL.
