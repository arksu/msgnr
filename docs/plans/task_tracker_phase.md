Ниже разбиение на фазы так, чтобы каждая давала законченный, проверяемый результат и могла быть принята отдельно.

# Принципы разбиения

Фазы собраны по таким правилам:

* каждая фаза даёт работающий инкремент;
* внутри фазы минимум пересечений по данным и API;
* после каждой фазы можно провести backend/frontend/QA-приёмку;
* ранние фазы уменьшают архитектурные риски: сначала конфигурация и ядро, потом операционные сценарии, потом аудит и уведомления.

---

# Фаза 0. Финализация контрактов и технический baseline

## Цель

Зафиксировать окончательные правила, чтобы дальше команды не расходились в трактовках.

## Что делаем

* замораживаем ТЗ;
* фиксируем DDL;
* фиксируем API-контракты request/response;
* фиксируем список бизнес-ошибок и их коды;
* фиксируем правила soft delete;
* фиксируем формат валидации `prefix`;
* фиксируем фильтрацию/сортировку списка задач;
* фиксируем правила уведомлений и роль поля `assignee`;
* фиксируем формат событий истории;
* создаём migration plan.

## Результат

Есть утверждённая спецификация, схема БД и контракты API, по которым можно независимо делать backend, frontend и QA.

## Что тестируем

* ревью схемы данных;
* ревью API;
* проверка, что все спорные места закрыты.

# Фаза 1. Базовая админ-конфигурация: шаблоны, статусы, enum-справочники

## Цель

Дать системе управляемую конфигурацию до появления задач.

## Что делаем

### Backend

* таблицы:

  * `task_template`
  * `task_template_sequence`
  * `task_status`
  * `enum_dictionary`
  * `enum_dictionary_version`
  * `enum_dictionary_version_item`
* CRUD для шаблонов;
* soft delete шаблонов;
* reorder шаблонов;
* CRUD для статусов;
* soft delete статусов;
* reorder статусов;
* CRUD для enum-справочников;
* создание новых версий справочников;
* чтение версий и состава значений;
* валидация:

  * уникальность `prefix`;
  * `prefix` только `A-Z`;
  * уникальность `task_status.code`;
  * уникальность `enum_dictionary.code`.

### Frontend

* экран списка шаблонов;
* создание/редактирование шаблона;
* удаление шаблона;
* экран статусов;
* создание/редактирование/удаление статусов;

## Что пока не делаем

* задачи;
* комментарии;
* вложения;
* история;
* уведомления.

## Результат

Администратор может подготовить каркас трекера: типы задач, статусы и глобальные enum-справочники.

## Что тестируем

* создание нескольких шаблонов;
* уникальность и формат `prefix`;
* soft delete шаблона;
* создание/удаление статусов;
* создание справочника;
* выпуск новой версии справочника;
* уникальность `code` справочников и статусов.

# Фаза 2. Поля шаблона и конфигурирование структуры задач

## Цель

Сделать шаблоны полноценными: администратор может задавать структуру задачи.

## Что делаем

### Backend

* таблица `task_field_definition`;
* CRUD для полей шаблона;
* soft delete поля;
* reorder полей;
* поддержка типов:

  * `text`
  * `number`
  * `user`
  * `users`
  * `enum`
  * `multi_enum`
  * `date`
  * `datetime`
* правила:

  * уникальность `code` в рамках шаблона;
  * `field_role = assignee` только для `user/users`;
  * не более одного активного `assignee` на шаблон;
  * для `enum/multi_enum` обязателен `enum_dictionary_id`.

### Frontend

* экран полей шаблона;
* форма создания/редактирования поля;
* reorder drag-and-drop;
* soft delete поля;
* выбор `field_role`.

## Что пока не делаем

* задачи;
* список задач;
* история;
* уведомления.

## Результат

Администратор может полностью сконфигурировать, какие поля будут у задач каждого шаблона.

## Что тестируем

* создание полей всех типов;
* soft delete поля;
* повторное использование `code` после soft delete, если это выбрано в БД;
* ограничения на `assignee`;
* корректность enum-полей и ссылок на справочники;
* порядок полей.

* `PATCH /tasks/:id`

* валидация и сохранение значений всех типов полей;
* сохранение `enum_dictionary_id + enum_version` и FK на версию справочника;
* запрет изменения `prefix`, если по шаблону уже есть задачи.

### Frontend

* форма создания задачи;
* выбор шаблона;
* динамическая перестройка формы при смене шаблона;
* карточка задачи;
* редактирование системных и пользовательских полей.

## Что пока не делаем

* список задач;
* подзадачи;
* комментарии;
* вложения;
* история;
* уведомления.

## Результат

Есть полноценная карточка задачи, задачи можно создавать и редактировать по шаблонам.

## Что тестируем

* создание задачи по разным шаблонам;
* генерацию `public_id`;
* независимую нумерацию по шаблонам;
* создание со всеми типами полей;
* работу обязательных полей;
* создание задачи при удалённом шаблоне — ошибка;
* использование удалённого статуса — ошибка;
* корректность хранения enum с версией.

# Фаза 8. Уведомления

## Цель

Закрыть реактивные сценарии без ручного контроля карточек.

## Что делаем

### Backend

* определение поля исполнителей по `field_role = assignee`;
* вычисление фактического изменения состава исполнителей;
* отправка уведомлений:

  * при назначении исполнителя;
  * при смене статуса;
* правило:

  * по смене статуса уведомления идут исполнителям;
  * если поля исполнителей нет, уведомления по исполнителям не отправляются;
* защита от дублей.

### Frontend / интеграция

* интеграция с существующим механизмом уведомлений мессенджера;
* отображение событий в UI уведомлений, если это входит в существующий контур.

## Результат

Исполнители получают сигнал о важных изменениях без необходимости вручную мониторить задачи.

## Что тестируем

* одно назначение;
* множественное назначение;
* отсутствие дублей при повторном сохранении без изменений;
* уведомление по смене статуса;
* отсутствие уведомлений, если assignee-поле отсутствует.
